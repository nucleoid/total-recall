# Bounded hosted array packing

The Native Qwen four-input/2,000-token request ceiling is a local inference transport bound, not an OpenRouter array limit. Keep the complete frozen vector descriptor and all per-input formatting, normalization, tokenization, chunk offsets, projection and dimension checks unchanged. Cloud batching groups independently formatted inputs; it does not concatenate texts or re-label a vector space.

`hosted-packed-worker.ts` requires a SHA-256-bound additive execution supplement tied to the existing run, base manifest/source, contract and immutable implementation release. It reuses the original operator/database/runtime/manifest/TLS checks. Parent/source/token/elapsed/attempt limits still come from the original manifest. Hosted and Native concurrency remain one.

The packing implementation stages at most the existing bounded number of parents, renews live generation leases every ten seconds (including while awaiting HTTP), separates document/query inputs, and packs up to 128 inputs / 32,768 measured tokens / 1 MiB request JSON. Responses are limited to 16 MiB. Each source chunk keeps a parent/ordinal mapping; every returned index/count/vector/provider/model/usage value must validate. Parent publication still uses the original atomic store generation, revision, lifecycle and run fences. A resource or explicit stop defers staged work without consuming attempts; provider retries apply only to parents whose inputs were actually submitted. Paid successful response usage is counted even if a subsequent cancellation prevents publication. Provider-wide systemic mismatches pause without stamping every staged parent as invalid.

DeepInfra's published OpenAI schema declares an input-array maximum of 1,024 (https://docs.deepinfra.com/api-reference/embeddings/openai-embeddings). Qwen's listed context is 32,768 tokens per input. The lower 128-input / 32,768 aggregate-token / 1 MiB ceilings above are our conservative operational bounds, not claims that they are provider-wide maxima. The OpenRouter route is independently checked with staged public and authorized-corpus requests before sustained rollout. No undocumented HTTP payload maximum is assumed.

Queue diagnosis found a separate PostgreSQL predicate-implication issue: the original pending/retry OR expired-claimed predicate did not select the ordered partial index. An explicitly redundant `state IN ('pending','retry','claimed')` predicate preserves selection semantics and makes the existing index usable. Existing frozen runners can instead use an additive equivalent OR-form partial index; never drop an active queue index to optimize it.

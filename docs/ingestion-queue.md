# Durable memory ingestion

`memory_store` (MCP) and `POST /api/store` can acknowledge a committed memory before its embedding provider recovers. Enable `MEMORY_INGESTION_QUEUE_ENABLED=true` only after applying migration 049 and starting the dedicated worker. The default is off and preserves synchronous storage. Content updates additionally require migration 050 and `MEMORY_INGESTION_UPDATE_ENABLED=true`. Documents require migration 052 and `MEMORY_INGESTION_DOCUMENT_ENABLED=true`. Session ingestion retains synchronous episode embedding; #161 owns adopting this path in `src/session-distillation.ts`.

## Documents

`memory_store_document` and `POST /api/store-document` atomically commit the document, every physical chunk with NULL embedding/identity, one shared-queue job per chunk (`kind=document`, no dedupe or contradiction classification), the idempotency hash/key, chunk count and acceptance audit. The response adds derived `state`: `ready` when all chunks are ready, `embedding_failed` when any failed chunk remains with no pending work, otherwise `queued`. Cancelled counts are explicit; cancellation alone does not imply readiness. No document state is stored. Existing synchronous documents count as ready. The default-off sub-gate preserves synchronous new writes.

Up to `MEMORY_STORE_DOCUMENT_INLINE_MAX_CHUNKS` chunks (default 8, range 0–64) use one bounded batch helper within `MEMORY_STORE_INLINE_EMBED_MS`. Larger documents make no inline provider call. The worker's `--batch-size` is 16 by default (1–64); each batch contains only one document, while store/update jobs remain scalar. Each physical chunk remains at most 2,000 UTF-8 bytes. Gemini/Ollama use the configured validated batch adapter. Under current Qwen serving, every physical chunk is separately planned into token-bounded local chunks and all its vectors are prepared through the pinned local runtime (native requests of at most four inputs), within the same overall budget. Approved legacy rollback additionally uses the existing reserved-input budget before the Gemini batch request. Dimension, finite-value, response-count and accepted-profile checks apply to the whole batch. No new provider/profile credentials or configuration format is required.

All compatibility-vector writes, current eligible target manifests/chunks, capture completion, ready transitions, subscription outbox effects and audits for a batch commit together after locking every current job/lease before its memories. Local publication retains migration 051's lease/content/profile and current lifecycle fences; target subscription routing stays authoritative after cutover. Batch failure records retries atomically with shared backoff using the highest batch attempt; the original per-job attempt policy remains. Expired leases recover forced kills after acceptance, claim, provider completion or an aborted finalization. `source_revision` records acceptance provenance; public metadata revisions do not invalidate a content generation. A later content edit replaces the job generation and stale batch results cannot land.

A rejected multi-chunk batch cannot identify the bad input. The jobs atomically return to pending with content-free `batch_input_rejected` markers and no per-chunk attempt charge for that unattributed batch rejection. Marked jobs claim singly on subsequent polls, including after a crash. Only a chunk rejected on its own becomes failed; healthy siblings finish ready. Transient batch errors retain shared backoff. Superseded/consolidated document generations cancel as in the scalar path, while update-kind historical indexing is preserved. If a batch loses a lease or contains an invalid memory after provider work, it lands no vectors, cancels only still-owned invalid jobs, and returns still-owned valid siblings to pending without spending an attempt. Newer generations remain untouched.

Identical idempotent replays return the same ID/current state in queued, partial, failed and ready states without new jobs or provider calls. A changed hash conflicts; tombstones retain the stable tombstoned conflict. Physical chunk counts and `repair:document-chunk-counts` are unaffected. Pending chunks remain in ordered recall, FTS and exports (`ingestion_state`); only embedded chunks enter vector search. Each chunk's recall includes ingestion state with owner-only detail.

`memory_document_status` and `GET /api/documents/{id}/status` require read permission, accepting ownership, namespace and access scope. They return `{ document_id, state, chunk_count, ready, queued, failed, cancelled, oldest_pending_age_seconds, failure_categories }` without content, title, credentials or raw errors. Nonowners (including other admins) receive 404. Forgotten chunks count as cancelled for the owner. `POST /api/ingestion/documents/{id}/requeue` requires admin permission in the namespace/access scope, resets only failed/cancelled live jobs and records operator/audit; ready, pending and tombstoned jobs stay unchanged. Queue stats include `pending_documents`.

Document first-readiness retains the existing chunk `memory.stored` subscription semantics. Update-kind jobs and episode chunks remain excluded. Migration 052 is a hard prerequisite for deploying either the new API or the new worker, even with the document sub-gate off: scalar claims also use its columns. Deploy migration, then worker, then API, then enable the document sub-gate; a 049/050/051 scalar worker can still drain document jobs singly, but pre-052 trigger behavior would suppress their events. Disable the sub-gate for rollback and keep the new worker running until pending work drains. `reembed` deliberately skips nonterminal queue jobs, so it is not a substitute for draining the worker. After draining, ordinary re-embedding can repair vectors while retaining terminal job history.

## Content updates

`memory_update` / `PATCH /api/memories/{id}` validates and locks as before, commits content/tags/metadata/supersession with all four old embedding fields cleared, and replaces the job generation in that transaction. The same bounded inline helper then tries embedding; provider failure leaves durable work for the worker. Update responses expose `memory.ingestion.state` as `ready` or `queued`, preserving terminal failure states. Recall/list expose the underlying `pending`, `processing`, or `retry_wait` detail. Owner-only timestamps/retries follow the existing status contract; other namespace readers see state only. An authorized namespace writer may replace another key's private job, but ownership stays with the existing accepting key (or the memory creator for a first job), preserving that creator's keyed-store retries and job-before-memory locking. A different editor gets state only and leaves indexing to the worker; the owner's inline helper cannot claim another key's job. The `memory.update` audit still identifies the actual editor. Job locking/reset uses scoped database functions without broadening job RLS. Legacy NULL memory access levels retain their existing normal-access semantics.

Tags, metadata and supersession-only edits never call the provider or reset/enqueue jobs. Public `revision` also increments on these changes and on consolidation, so it is accepted provenance (`source_revision`), not a content-only fence. The current locked job and live lease token identify the accepted generation; matching content, namespace/access, NULL embedding and deletion/expiry guards protect completion. Every queued content edit replaces that generation, including A→B→A; stale results/failures cannot land. Existing synchronous content writers replace content/vector together, so their completed vectors are observed without overwriting them. An update may finish a historical superseded/consolidated row without reopening it. Normal consolidation itself requires a ready vector and matching membership; NULL-vector rows cannot be newly consolidated through that operation.

Update jobs never dedupe or revise beliefs. Finalization only fills vector fields and completes the job; it does not change `updated_at` or public revision, so `If-Match` stays tied to the user's patch. An update-kind finalize never creates subscription events, including replacement of a still-pending original store (that first store event is intentionally suppressed). Forget prevents completion; hard purge cascades the job. Disable either gate to preserve synchronous updates; retain the new worker while draining accepted jobs. See [migration 050 rollout](rollouts/050-memory-ingestion-updates.md).

Acceptance validates permission, namespace, access level and TTL, resolves the agent, then commits the real memory with a NULL embedding, a content-free job and an audit event in one transaction. Database failure is never acknowledged as acceptance. The UUID is the real memory ID. TTL starts at acceptance, not readiness.

With the gate enabled, store responses keep the existing required fields and add `state: ready | queued | embedding_failed | cancelled` and `accepted_at`. A queued response has `created: true`, `deduplicated: false`, and no similarity. Identical keyed retries return the actual terminal state and the same ID without silently restarting a failed/cancelled job. Inline finalization also reports a detected terminal state, rather than promising further processing. Recover with the admin requeue procedure or correct the keyed content. Healthy inline completion returns the normal result, including the actual canonical ID and similarity on dedupe. `MEMORY_STORE_INLINE_EMBED_MS=3000` bounds inline provider work (embedding and any mutation classification) independently of `EMBEDDING_TIMEOUT_MS`; `0` makes acceptance always asynchronous. Database acceptance/finalization time is additional. If a provider ignores cancellation, its late result cannot finalize.

Jobs move from `pending` to `processing`, then `ready` or `deduplicated`. Retryable errors move to `retry_wait`; invalid input/vector or exhausted retries become `embedding_failed`. Expired/forgotten memories are cancelled. A processing lease can be reclaimed after a crash. Every completion and failure is fenced by a fresh lease token, so a stale process cannot boost, revise, audit or notify twice.

Pending and failed content remains recallable, listable, exportable and full-text searchable. It is absent from vector ranking until ready. When migration 049 is present, recall/list/search expose `ingestion`; the accepting owner sees timestamps, attempts, retry time, failure category and canonical ID, while other readers see state only. A deduplicated accepted ID resolves to the current authorized canonical row for its accepting owner. Forgetting or expiry still prevents recall. Exports add `ingestion_state`; import always generates destination embeddings and never trusts that advisory state or transfers vectors.

Idempotency keys retain the same key-scoped hash and memory UUID. Identical pending/retry/processing requests do not create another job or acceptance audit. Identical ready requests refresh metadata without re-embedding. The existing memory is locked after its job before deciding whether content is unchanged, so concurrent synchronous writers cannot separate stored content from its vector. Changed content, namespace or access invalidates the lease and clears the old vector/identity together, resetting processing/ready/failed jobs to pending. A tombstoned, superseded or inaccessible keyed row is never revived. Queued responses use created:true for acceptance; healthy keyed updates retain created:false, and keyed acceptance audit details retain idempotent:true.

Dedupe takes the existing namespace/access advisory lock, excludes the pending row and matches only current eligible rows in the same vector space. The canonical row is boosted and the pending row is soft-deleted. Contradiction classification runs before any finalization row/advisory locks. The fenced transaction revalidates its predecessor and finalizes the accepted row as successor; stale predecessors or constraint failures fall back to normal semantic dedupe after rolling back any revision savepoint effects, or to an unlinked ready row if no duplicate qualifies. Its existing policy, budget and scope gates still apply; shadow classification is scheduled after commit and excludes the finalized ID.

## Worker and retry policy

```sh
node dist/ingestion-worker.js --concurrency 4
node dist/ingestion-worker.js --once --max-jobs 100
```

The worker uses `INGESTION_WORKER_API_KEY`, a dedicated enabled admin key with the namespaces to drain. Claims use its admin scope, but content/finalization uses the accepting owner's ID and exactly one namespace. Revoking the accepting key after durable acceptance does not discard that write. Revoking the worker key stops new polls. Concurrency is 1–32, default 4; `--poll-ms` accepts 100–60000. Stopping API acceptance does not stop backlog drainage.

429 retries as `rate_limited`; 408/425/5xx, timeouts and transport failures retry as `transient`; 401/403 retry as `provider_auth` at the twelve-hour cap so credential outages do not dead-letter the backlog. 400/404/413/422 and invalid vectors fail immediately on worker attempts. `MEMORY_INGESTION_MAX_ATTEMPTS` defaults to 12; inline attempts do not consume this allowance. Retries reuse the webhook schedule of 1m/5m/30m/2h/12h with positive jitter and Retry-After up to the twelve-hour cap. Raw provider messages, content and credentials never enter job errors or metrics.

Database lock/statement timeouts, deadlocks and serialization failures (`55P03`, `57014`, `40P01`, `40001`) retain category `transient` with content-free code `db_contention`. They roll back finalization. At most one failure in a consecutive contention streak receives a free one-second worker retry; repeated failures consume the normal attempt allowance and use its jittered 1m–12h backoff, eventually becoming embedding_failed. An inline contention handoff records the same code, so it also prevents a second free retry in that streak. Inline contention hands off immediately as pending. Monitor persistent contention separately from provider outages.

Jobs snapshot the active provider/model/dimensions at acceptance. A changed space fails as `space_mismatch`, rather than writing an incompatible vector. Requeue preserves the accepted target; restore that profile to retry, or use the reviewed re-embedding procedure to repair vectors. Re-embedding does not rewrite terminal job history.

## Operations

All control endpoints require admin permission and remain available for draining when API acceptance is off:

- `GET /api/ingestion/stats`: depth by status, oldest pending age, attempts histogram, failure categories, next retry, inline hit rate and last worker heartbeat. `memory_stats` includes this block when migration 049 is present.
- `POST /api/ingestion/pause` and `/api/ingestion/resume`: pause/resume new worker claims; in-flight jobs and inline requests finish. Changes are audited.
- `POST /api/ingestion/jobs/{memory_id}/requeue`: reset a live failed/cancelled job, record operator and timestamp, and audit. Ready, deleted, expired, missing and out-of-scope jobs return 409.

The admin dashboard Overview shows queue depth, age, heartbeat, inline hit rate, retries and pause/resume. Memories have ingestion state badges. No queue metric includes memory content. The worker only receives content under one accepted namespace's scope.

Migration 049 adds a disabled pending-to-ready subscription trigger. Enable it together with the insert trigger when subscriptions are live. The existing outbox identity makes repeated finalization harmless. Content updates do not create events; the pending-to-ready transition is the creation event. `episode_chunk`, sensitive and secret memories remain excluded.

See [the rollout and recovery runbook](rollouts/049-memory-ingestion-queue.md).

If an existing synchronous writer fills a pending row's vector, claim/finalization observes that vector and completes the job without dedupe, revision or overwriting the edited content. A different vector identity cancels the queued generation. Re-embedding skips pending/processing/retry_wait jobs at selection and write time. The ready trigger requires a nonterminal ingestion job, so filling a historical NULL vector does not create subscription events. An inline claim/finalization/failure-recording error after acceptance returns queued; the lease recovers it. Continuous workers use settled per-job results and bounded poll backoff across database failures, while --once reports an incomplete poll as an error.

Read/export status and canonical aliases follow schema presence, independently of the acceptance gate, so disabling new acceptance retains visibility while the worker drains. Inline deadline exhaustion hands immediately to the worker as pending; actual provider errors retain their backoff. Expired processing leases at the maximum worker attempt count become embedding_failed/transient. Worker leases cover the embedding timeout plus the approved mutation-classifier timeout and a 30-second margin, with a 150-second minimum.

The owner-approved amendment to #157 preserves approved high-confidence corrections before semantic dedupe, matching the existing synchronous priority. Both inline and worker finalization attempt the prepared revision first; a successful revision keeps the accepted ID as the successor even when its vector is a near-duplicate. If classification yields no applicable revision, or its predecessor becomes stale, normal dedupe runs. Existing mutation approval, confidence, scope and budget controls still apply.

When the remaining inline deadline is shorter than the full configured classifier timeout, the job defers to the worker before any classifier reservation or provider call. The worker then evaluates with its full timeout. Eligible classification runs even on near-duplicates; there is no duplicate shortcut that can discard a correction. This can spend approved classifier budget on inputs that ultimately dedupe. The final transaction takes the existing namespace/access lock before predecessor/canonical row locks, attempts the prepared revision, then runs dedupe only if no revision commits. SIGTERM stops new polls and drains claimed work within the unit stop budget, without charging shutdown as a provider failure. Immediate handoff timestamps use the database clock.

Classification finishes and releases its database sessions before the final transaction begins. The final lease, content, access, expiry and embedding-profile guards still apply to both outcomes. Concurrent corrections revalidate the predecessor under lock: one revision can commit; another stale preparation may dedupe to that committed successor. Repeated finalization cannot repeat boosts, revision audits or outbox effects.

`CONTRADICTION_COST_BUDGET_USD` remains a process-lifetime reservation cap, not a shared spending ceiling. Each API replica and ingestion worker receives a separate cap; restarts and each `--once` invocation reset reservations. Before enabling classification/mutation with the queue, operators must explicitly approve and split caps across every API and worker process, accounting for canaries and restarts. Do not repeatedly drain with `--once` under the assumption that one previous approval provides an aggregate cap. To move queued-store classification to the worker, set the API's inline budget to `0` while preserving the approved mutation policy in the worker; disabling only API mutation while still finalizing inline would discard corrections. This change does not add a database-backed budget ledger. Retries after ambiguous provider completion can still consume another reservation.

Acceptance-time authorization preserves completion of the accepted row after its key is disabled, revoked, expired or narrowed. Effects on other memories require that the accepting key currently has write permission in the job's namespace and access-level ceiling. Only a possible cross-memory effect takes a key-row fence, after acquiring the namespace lock. Finalizers serialize on that fence rather than joining shared holders ahead of a waiting revoker. Revocation either takes effect first and prevents those effects, or completes after the already-authorized transaction commits. Classification holds no such lock; authority lost during classification is rechecked before mutation. Without authority the accepted row still finishes ready, with no canonical boost, tag merge or new predecessor supersession. Its ID remains stable, and any existing explicit predecessor link is preserved.

For stronger incident containment, stop acceptance and pause claims, account for in-flight work, and forget affected accepted memory IDs through the existing lifecycle tooling. Listing queued IDs by accepting key requires an authorized database query: the HTTP stats endpoint is aggregate-only. Pausing is not cancellation, and this change introduces no cancel-by-key API.

The first ready transition of a newly accepted memory may emit its subscription creation event. A separate `creation_pending` flag survives keyed replacements before that first readiness and is consumed when any generation becomes ready or deduplicated. It is independent of the current upsert's `created` response. After first readiness, keyed content replacements do not create newly matching events. Every required memory UPDATE must affect one row before readiness/dedupe can commit; suppressed or RLS-denied updates roll back vector, canonical effects, outbox and audit together.

Inline mutation preparation applies only to the approved normal-access namespace. Stores outside that scope, including sensitive and secret content, retain their healthy inline embedding fast path even when mutation is enabled elsewhere. Dashboard memory cards display the ingestion state as text; terminal states are also distinguished visually.

Authentication never waits merely to update `last_used_at`: a busy key row skips that telemetry write and checks current committed key validity through the read-only path. The usage timestamp is therefore best-effort under contention; revocation and expiry checks remain mandatory. Finalization bounds each lock acquisition to five seconds and each SQL statement to fifteen seconds. A timeout rolls the transaction back and retries through the existing queue; accepted content remains durable. Keyed/TTL or other unlinked completions with no possible cross-memory effect take no key-row fence. Explicitly linked pending successors are embedded in place without revision or dedupe, so queue completion cannot delete the only successor in an existing belief chain.


The REST Memories list and detail endpoints expose the same ingestion metadata as MCP; the accepting owner’s deduplicated ID resolves to its authorized live canonical row. Metadata-only keyed refreshes write a store audit when fields change, while identical no-op refreshes do not duplicate acceptance audits. The job’s original accepted actor/security snapshot remains the attribution for finishing that original work.

Live queue monitoring and optional retained-history aggregates use separate transactions, each with a five-second statement timeout and normal planner settings. History timeout preserves active depth, oldest age, next retry, paused state, heartbeat and failure alerts. history_available:false and depth_scope:nonterminal explicitly mark partial history; attempts_histogram is then an unavailable placeholder and inline_hit_rate is null. With history available, depth_scope:all and the history histogram/hit rate are populated. Failure categories always count current nonterminal failures plus terminal failures finalized within the last 24 hours, using the partial claim and recent-failure indexes. A failure of core monitoring can still omit the optional ingestion block from memory_stats without failing committed base statistics. The dedicated endpoint can then fail independently. Job history and owner aliases remain until the memory is purged; this change adds no automatic deletion policy. Monitor query latency and plan maintenance explicitly rather than deleting alias history to improve metrics. Admin metrics and requeue also enforce the key’s access-level ceiling.

Release builds use npm run build, which compiles src/ingestion-worker.ts to dist/ingestion-worker.js with the existing server build. Deploy dist plus production dependencies in the immutable release, then point current at it; the systemd unit runs native Node and needs neither tsx nor TypeScript sources. npm run ingest:worker remains a development-source entrypoint.

Transfers include failed and pending content and re-embed at the destination. If the destination provider also rejects a record, its entire import batch fails atomically, preserving the existing transfer contract. Archive the complete original feed, isolate the rejected records (ingestion_state can identify known failed candidates), and import the remaining validated records as a separate feed. No automatic skipping or content loss is introduced; a source failure does not prove the destination will reject it.

Worker startup uses the shared symlink-aware entrypoint helper. Both native release and development entries are tested through a current-release directory link; the smoke test verifies main runs rather than merely importing the module.

Cross-memory finalization intentionally serializes each accepting key across namespaces to queue behind revocation. The key fence precedes candidate row locks, matching delivery lock ordering. Start single-key canaries at concurrency1, measure cross-namespace key-lock wait,55P03 counts, finalize latency and provider/classifier retries before increasing concurrency. Keep serial drainage or improve a measured slow query if key waits approach5s; more worker concurrency cannot improve that critical section. Inline SQL lock waits are additional to its provider budget. Repeated contention uses bounded backoff/attempts.

## Local target-space integration

With the attested local serving contract active, durable stores and updates prepare every lossless document chunk before acquiring parent locks. The current job lease/content fence, compatibility vector, full chunk manifest, readiness and audit commit atomically. A stale lease cannot publish a replaced update. Local dedupe uses semantic matching only when both parents contain one chunk; if either parent is multi-chunk it requires complete source identity, so shared boilerplate cannot discard novel content. Comparison stays under the same namespace/access lock, excluding unembedded pending queue rows; incomplete indexed candidates still fail closed. Synchronous queue-off content updates use the same atomic local publication.

Apply compatibility migration 051 before enabling queues with local serving. It preserves the disabled-by-default subscription triggers, routes target matching only through complete manifests, and suppresses update-kind events even when a content update replaced a still-pending original creation. Legacy readiness matching remains creation-only. Migration installation is not cutover approval or runtime-capacity evidence.

# Rollout 037: durable memory ingestion

This is an operator procedure, not authorization to migrate a live database. No production migration, merge or deployment is part of implementation #157.

## Integration prerequisite

Pinned main ends at 036. This change adds `037_memory_ingestion_queue.sql`. Open PR #158 at `420a42dabcf692d02b42294b9f2f3a65c5c328f6` independently introduces migrations 037–047 and changes embedding/store/search. The migration loader rejects duplicate numeric prefixes. Combining these branches verbatim is invalid. Before integrating either branch, coordinate migration numbering/order and re-review embedding identity, keyed store, search and migration checksums on the actual combined head. Never rename an already applied migration or rewrite its checksum. No compatibility with PR #158 is asserted here; that branch has not been incorporated or tested.

## Canary

1. Keep `MEMORY_INGESTION_QUEUE_ENABLED` unset/false. Back up the database and use the existing owner-only `MIGRATION_DATABASE_URL` procedure to apply 037. It creates an empty job table, indexes, RLS, two instance settings fields and helper functions; it performs no content/vector backfill. Foreign-key/trigger DDL on memories and ALTER TABLE on instance_settings require table locks. Migration 037 sets transaction-local `lock_timeout = '5s'` to bound each DDL lock acquisition. `MIGRATION_LOCK_TIMEOUT_MS` controls only the runner's advisory-lock wait and does not bound table locks. Use a low-traffic window; on SQLSTATE 55P03, let the entire migration roll back, identify and resolve the long-running transaction, and retry normally. Never write the ledger manually or bypass contention guards. The migration also qualifies the existing outbox matching query's ambiguous output `id`; historical migrations are unchanged.
2. Deploy the reviewed binary with acceptance still off. Create a dedicated enabled API key using `npm run create-key` and the normal key-management procedure. Give it admin and only the required namespaces. Store it as `INGESTION_WORKER_API_KEY` in the worker environment; do not reuse client credentials. Existing client keys and sessions need no rotation or reauthentication.
3. Configure the same active embedding profile and approved contradiction policy in API and worker. Before enabling mutation, explicitly approve and allocate `CONTRADICTION_COST_BUDGET_USD` separately for every API replica and worker, including canaries and expected restarts. Each process has its own lifetime cap; restarts and each `--once` invocation reset it. There is no aggregate cross-process ledger. Do not use repeated `--once` runs as though they share an existing cap. Set the API inline budget to `0` if queued-store classification should be confined to the worker; do not merely disable API mutation while allowing inline finalization. Start `node dist/ingestion-worker.js --once --max-jobs 10 --concurrency 1` as a canary under that allocation, then use `deploy/systemd/total-recall-ingestion.service` for continuous service. Verify `GET /api/ingestion/stats` reports a fresh heartbeat and no unexpected pause.
4. If subscriptions are live, as owner enable **both** `memories_subscription_enqueue` and `memories_subscription_ready_enqueue` on public.memories. These database-side switches are independent of API flags. Verify exactly one ID-only outbox entry for a normal canary and none for sensitive/secret or episode chunks.
5. Enable `MEMORY_INGESTION_QUEUE_ENABLED=true`, initially in the intended namespace. Default inline budget is 3000ms; use `MEMORY_STORE_INLINE_EMBED_MS=0` for always async. Healthy stores not eligible for mutation (outside its approved scope, sensitive/secret, keyed or TTL) return ready when embedding fits the budget. An eligible unkeyed normal-access store in the approved namespace deliberately hands off when the remaining budget is shorter than the full classifier timeout: with the default 3000ms inline and 10000ms classifier settings, queued is expected even with healthy embedding. The worker re-embeds and classifies; use always-async to avoid that discarded inline probe. Verify stable IDs and queued recall/list/full-text/export visibility, then worker recovery. Canary a high-similarity correction through the worker and confirm its accepted ID remains the successor. To exercise inline correction separately, deliberately allow embedding latency plus the full configured classifier timeout in the inline budget; do not treat the default handoff as canary failure or raise the budget merely to make it say ready. Both completion paths must preserve the accepted correction ID, and ordinary duplicates must resolve to the canonical ID after completion.
6. Watch depth, oldest age, failure categories and heartbeat. Suggested initial alerts: oldest nonterminal job >15 minutes for 10 minutes, any input/space failures, or heartbeat >3 poll intervals plus 30 seconds. Tune to provider capacity; no alerting infrastructure is installed by this change. Increase concurrency only within provider quotas, up to 32.

The default worker provider timeout is 15 seconds (`EMBEDDING_TIMEOUT_MS`, max 120 seconds). A worker lease is at least 150 seconds and expands to cover embedding timeout + approved mutation-classifier timeout + 30 seconds, allowing recovery after crashes. Inline leases include a 30-second finalization margin. The inline budget bounds embedding and mutation-classifier work; acceptance and short finalization SQL time is additional. Classification holds no database row or advisory locks.

## Recovery

- Provider rate limit/outage: leave content visible, reduce concurrency, inspect only content-free stats. Retry uses jitter/Retry-After. No hot-loop retries. Inline attempts do not consume the 12 worker-attempt allowance.
- Database contention: inspect `db_contention` job codes separately from provider outages. Inline work hands off pending; at most one contention failure gets a free one-second worker retry; repeated failures use normal jittered backoff and the attempt cap, bounding embedding and classifier spend. During canary, measure finalization and revocation latency and inspect the dedupe query plan on the largest namespace; resolve persistent lock waits or slow scans before increasing concurrency.
- Provider authentication: repair credentials in the existing secret store, restart affected processes, allow capped retries. They do not dead-letter the entire backlog.
- Input rejected: correct the keyed content (same memory ID, new fenced job) or, after resolving the cause, admin requeue the affected ID. Requeue is audited; ready jobs cannot be requeued.
- Embedding space mismatch: never label the old vector as new. Restore the accepted active profile and requeue, or follow `npm run reembed`'s separate repair process. Re-embedding skips active jobs and repairs other vectors without creating historical subscription events; terminal ingestion history remains intact. There is no automatic backlog retargeting.
- Stuck processing: wait for lease expiry, then let the worker reclaim. Never manually clear live leases. Late finalization is fenced.
- Pause/drain: POST pause stops new worker claims while in-flight work finishes; inline stores still operate. Disable API queue acceptance if no more jobs should be accepted. POST resume before `--once` if the worker should drain due jobs. `--once` drains currently due claims; future retries require subsequent polls/runs.
- Forget/purge cancels via soft-delete checks or FK cascade; expired jobs cancel without consuming provider work when detected at claim. Expiry during embedding is checked again at finalization.

## Rollback

Disable API acceptance first. Keep the worker on the reviewed binary while draining; future retries require waiting or a later run. Stop the ingestion unit after the backlog is handled. Retain the additive schema and accepted rows. If rolling back subscription behavior, disable both subscription triggers; enablement of only the insert trigger loses pending-to-ready events. Do not drop the queue table to roll back.

Old API binaries ignore jobs and do not create NULL-vector rows. They can read pending text, but do not expose ingestion metadata or canonical aliases. Do not run old content writers against still-pending keyed jobs: the new finalizer checks content/access and the token before writing, but old binaries do not participate in queue reset semantics. Prefer drain before rolling back writers. No downtime, backfill, reindex or data deletion is required by this migration; lock acquisition must still be controlled. Provider and worker access are new operational permissions and must follow existing approval and secret handling procedures.

Ingestion visibility and aliases remain available with acceptance disabled whenever 037 is present. Inline budget exhaustion is immediately claimable; provider errors still back off. Expired poison leases stop at the maximum attempts and retain their content for audited requeue. The systemd stop budget covers the maximum configured provider/classifier work.

Do not repurpose an accepting writer key as a reflection-only key while jobs remain active: migration031 deliberately denies general memory mutation for reflection keys. Create a separate reflection key and disable the old writer key instead; revoked/disabled keys and ordinary write/namespace removal do not orphan accepted jobs. This rollout introduces no requirement to modify existing client permissions.

The owner approved preserving high-confidence contradiction revisions before semantic dedupe, superseding the original #157 dedupe-first sequence. Both API and worker use the same queued finalize primitive and priority as the existing synchronous path. A stale or inapplicable prepared revision falls back to normal dedupe, or a distinct ready row on a dedupe miss. Near-duplicates remain eligible for approved classification and consume its existing budget; check classifier capacity and budget in the canary. No new mutation scope or provider permission is granted by this ordering change.

On normal SIGTERM the ingestion worker finishes its claimed batch before exiting; the unit's 240-second stop budget covers the configured provider/classifier work. A forced kill instead recovers through leases. Short inline classifier deadlines hand work to the worker instead of permanently skipping a revision. The priority decision is approved and implemented; deployment still requires a clean review of the amended patch and the existing operational approvals.

Inline classification starts only when its full configured timeout fits in the remaining inline budget and the job is actually inside the approved normal-access scope, so unrelated namespaces and sensitive/secret stores keep their healthy inline fast path. Provider timeouts or ambiguous completions can still cost a second reservation on retry.

The owner-approved revocation boundary keeps accepted rows durable but withdraws authority over other memories. Dedupe/tag boosts and predecessor supersession require a currently enabled, unrevoked, unexpired accepting key with write permission for the accepted namespace and access level. Only possible cross-memory effects take a key-row serialization fence, after namespace contention has cleared. Later finalizers queue behind a waiting revoker. Authentication skips a contended `last_used_at` telemetry update and checks key validity read-only, so this fence does not block credentials merely for usage bookkeeping. Finalization uses transaction-local five-second lock and fifteen-second SQL-statement timeouts; failures roll back and retry without losing acceptance. Lost authority during unlocked classification is rechecked before committing any revision. With authority absent, the accepted row finishes ready without new canonical/predecessor mutations. Already explicit predecessor links are preserved and bypass queue revision/dedupe. Canary these boundaries, including concurrent same-key authentication and revocation, before widening rollout.

For stronger compromised-key containment, stop acceptance and pause claims, account for in-flight work, and forget affected accepted memories through the existing lifecycle tooling. Listing that key's content-free job IDs requires an authorized database query; no HTTP job-list-by-key or cancellation endpoint is provided. Revocation does not discard accepted content, and pausing is not cancellation.

Build the release with npm run build and deploy dist plus production dependencies. The worker unit runs current/dist/ingestion-worker.js with native Node, requiring no TypeScript loader or source tree. Queue metrics are independently bounded; an unavailable ingestion block must not be treated as an empty queue.

The live monitoring query remains independent of optional whole-history aggregates. Alert failure categories cover active failures and terminal failures from the last24h, backed by a recent-failure partial index. history_available:false means history counts are incomplete, not an empty queue; live backlog and heartbeat remain usable. During a single-key canary measure cross-namespace key-fence wait/55P03 and retries before raising concurrency from1. The fence deliberately preserves revocation ordering and adds at most the configured lock wait beyond the inline provider budget. Verify the continuous unit remains active and heartbeat advances through current, rather than relying on a one-shot canary heartbeat.
